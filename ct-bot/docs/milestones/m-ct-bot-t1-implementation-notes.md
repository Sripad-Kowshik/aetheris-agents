## The wrap

`ct-bot/agents/main.exs` is a single `%Aetheris.RunConfig{}` — no OrbConfig,
no peer ids, no spawn. Wrapper fields follow the sibling shape: `run_id`
minted outside the struct (`ct-bot-main-#{Aetheris.ID.generate()}`),
`sandbox_path` from `__ENV__.file`, `CT_BOT_MODEL`/`AETHERIS_MODEL` env
fallbacks, `mode: :record`, `context_strategy: :full`, `overlay_base_dir:
nil`, `max_steps: 4` (the payslip single-command figure — a tools-less
responder needs no more), **`tools: []`**, and a one-line `user_prompt`
fixture that exists only so the file evaluates and is marked as such
("T1 fixture turn — not a live host turn; the context bag arrives with
T7").

The `system_prompt` is the body of `ct-bot/docs/agents/main.md` copied
**verbatim**, written flush-left inside the heredoc so a diff against the
source file shows exactly the wrap and nothing else. No rule is restated,
summarised, or softened.

## The matrix half of the registration (T0's deferral discharged)

`agents/capability_matrix_ct-bot.exs` (copy of the email section agent;
four values changed per the runbook: `agents_dir` `ct-bot/agents`,
`scripts_dir` `ct-bot/scripts`, section file `docs/.sections/ct-bot.md`,
heading `## CT-Bot`; run_id `cap-matrix-ct-bot-…`; label `cap-matrix:
ct-bot`) and the `SECTIONS` entry `("ct-bot", "ct-bot")` — placed after
`cloudcost`, matching the sorted sweep order. The section describes the
use case from its files; it embeds no prompt text. The section file itself
(`docs/.sections/ct-bot.md`) is generated by a run of this agent, which
needs the harness sprint case — still a later harness commit, unchanged
from T0; until then the assembler tolerates the missing section with a
WARN, and `use_case_registry` checks only the agent file and the
`SECTIONS` key, both of which are present.

**Two instrument facts the ticket's naming collided with, both resolved in
 favour of the instrument and recorded here:**

1. **Filename.** The ticket named `agents/capability_matrix_ct_bot.exs`
   (underscore). The drift check's arm-4 derivation is
   `stem.replace("capability_matrix_", "")` compared against registry ids
   with `/` → `_` — for the id `ct-bot` there is no slash to replace, so
   the stem must be `ct-bot` and the file is
   `agents/capability_matrix_ct-bot.exs`. Same for the SECTIONS key
   (`("ct-bot", "ct-bot")`, not `("ct_bot", …)`) and the section file
   (`ct-bot.md`). The underscore spelling would have left both matrix arms
   red with no way to satisfy them.

2. **Regex widened.** Arm 3's SECTIONS parser
   (`scripts/drift_check.py:1397`) matched `([a-z0-9_]+)` — written when
   every agent-bearing id was hyphen-free — and could not parse `ct-bot`
   at all. Widened to `([a-z0-9_-]+)`, the same charset the registry's own
   row regex (`[a-z0-9/_-]+`) has always admitted. `tests/test_drift_check.py`
   passes unchanged (its synthetic fixtures are hyphen-free; `beta_one`
   parses identically under both classes). First hyphenated agent-bearing
   id in the repo; the class widening is the generalisation, not a
   ct-bot-specific carve-out.

## One registration surface the ticket did not name: the classifier

The first `label:` in a new `.exs` is watched by
`tests/test_run_classifier.py` — every declared agent label must classify
under Rig's run-list prefixes, or the run falls into Unclassified. So the
same change adds `ct-bot → CT-Bot` to **both** `USE_CASE_PREFIXES`
constants (`rig/src/components/modules/harness/RunList.tsx` and
`rig/src-tauri/src/commands/usage.rs` — two surfaces, one claim, kept
identical per the guard's own DIVERGENCE check). `rig/` is this repo, not
the harness; the two constants are Rig's own classifier data, and this is
the flow the guard exists to force. `main.exs`'s label
("CT-Bot Main Panel Agent") matches the new prefix; the section agent's
label ("cap-matrix: ct-bot") matches the existing `cap-matrix` prefix.
