## 1. Scope

The capability: **`run_command` accepts `curl` as a permitted command
name**, so an agent can run an HTTP call — fixed arguments of the shape
a `GET` or a `POST` — and receive the command's exit code.

The addition is **one name in one const**. The rule the const enforces
stays exactly as it is: a fixed argv vector, no interpreter grammar. No
pipes, no redirection, no shell strings — and no recomposition of the
request: the method and URL live entirely in args, passed through as
given, exactly as the script path did for `bash` (BL-292) and the
sub-command did for `docker` (BL-293).

## 3. Contract

**C1 — One addition to the const.**
`PERMITTED_COMMANDS` (`runner.rs:33-54@H`) gains `"curl"`. Nothing
else in the const moves — the BL-292 (`"bash"`) and BL-293
(`"docker"`) entries and their comments stay; `is_permitted/1`'s
basename matching (`runner.rs:60-66@H`) is untouched.

**C2 — Two refusal pins flip, one example moves, nothing is silently
dropped.** Curl is an asserted refusal in two test sites and one doc
comment, and each site pins something real:

- `non_permitted_command_is_blocked` (`runner.rs:274-281@H`) drops its
  `!is_permitted("curl")` line (`:276@H`) — `wget` stays refused, the
  test's subject unchanged. The BL-292 precedent (a comment recording
  the flip in place) is the shape.
- `path_traversal_attempt_is_blocked` (`runner.rs:283-287@H`) asserts
  `!is_permitted("../../bin/curl")` and `!is_permitted("/usr/bin/curl")`
  (`:285-286@H`) — written when curl *was* the refused name its
  traversal pin was demonstrated against. With curl permitted, both
  assertions are false. The test's subject is the **basename
  semantics** (a full path resolves through the final component), not
  curl; T1 repoints both assertions at a still-refused name — `wget`
  is the one already pinned refused — so the semantics pin survives
  with the same strength. Deleting the test is not an option; the
  basename-resolution pin is the only guard of its kind.
- The doc comment above `is_permitted` (`:57-59@H`) uses curl as its
  refused example ("`../../bin/curl` → `curl` → not permitted"); T1
  updates the example to the still-refused name it repointed the test
  to, so the comment and the pins agree.

The positive arm gains the pin: `permitted_basename_is_allowed`
asserts `is_permitted("curl")` beside the BL-292 bash and BL-293
docker pins. The const change and the test changes land together; one
without the other is a red build or a silent widening, and both are
wrong.

**C3 — A fixed-args call returns the command's exit code.** A
`run_command` call with `command: "curl"` and fixed args — a `GET` or
a `POST`, passed through as given — flows through the existing `run`
path unchanged (`runner.rs`, `run_with_env`) and returns whatever
`RunResult` already returns: the command's `exit_code`, `stdout`,
`stderr`. Nothing in the dispatch or the timeout handling changes.
The dispatch path itself is name-agnostic and proven twice — BL-292's
bash pin (`runner.rs:206@H`), BL-293's docker pin (`:225@H`); whether
T1 adds a curl runtime pin or relies on that precedent is the STOP
item below.

**C4 — Everything else stays refused.** The refusal path
(`main.rs:444-459@H`) is untouched; every name still absent from the
const — `wget` foremost, now that curl joins — is refused exactly as
before. The allowlist's size grows by one; its semantics grow by
zero.

**C5 — No next name is filed here.** The series has now named and
discharged bash (BL-292), docker (BL-293), and curl (this row); no
further same-shaped admission is filed by this brief. The next ask —
if one comes — gets its own row, evidence, and brief.

## 5. Open for plan STOPs

- The runtime-pin shape for a network-touching binary: a real `GET`
  needs a reachable URL, which a unit test cannot promise. Options T1
  weighs: pin at `is_permitted` level plus the two dispatch precedents
  (no new runtime test), or a network-free runtime pin (`curl
  --version` is answered by the binary alone, the BL-293 `--version`
  precedent) if T1 prefers a third dispatch-level pin. T1 decides and
  says so; the done-when's exit-code arm is about the path, not a
  live HTTP call.
- Whether the tool description's curl wording needs any note (timeouts
  on slow endpoints, body size) — today the timeout/kill path exists
  (`run_with_env`) and the brief adds no rule; if T1 finds the
  description's wording already settles it, no new rule is written.
- Whether `curl` travels on every platform the exec server serves —
  the const has no platform gating (F1), and the default is the
  file's existing shape: one flat list.
