## 1. Scope

The capability: **`run_command` accepts `bash` as a permitted command
name**, so an agent can invoke an existing shell script — a script path
plus fixed arguments — and receive the script's exit code.

The addition is **one name in one const**. The rule the const enforces
stays exactly as it is: a fixed argv vector, no interpreter grammar. No
pipes, no redirection, no shell strings — `bash` is admitted as an
executable that takes a script path and arguments, not as a door
through which arbitrary shell syntax returns.

## 2. Tranches

- T0 — this brief.
- T1 — the harness implementation: C1 and C3 below, plus the unit-test
  flip C2 requires (a deliberately-pinned refusal cannot stay pinned
  while the name is admitted — the same test file gains the positive
  assertion).

## 3. Contract

**C1 — One addition to the const.**
`PERMITTED_COMMANDS` (`runner.rs:33-50@H`) gains `"bash"`. Nothing else
in the const moves; `is_permitted/1`'s basename matching
(`runner.rs:56-64@H`) is untouched.

**C2 — The pinned refusal is flipped deliberately.**
`non_permitted_command_is_blocked` (`runner.rs:234-239@H`) drops its
`!is_permitted("bash")` assertion (`:238@H`) and the refusal claim it
carries; `permitted_basename_is_allowed` (`:221-227@H`, or the same
test — T1's placement) gains `is_permitted("bash")`. The test change
and the const change land together; one without the other is a red
build or a silent widening, and both are wrong.

**C3 — A script call returns the script's exit code.** A
`run_command` call with `command: "bash"` and a fixed args vector —
script path plus arguments, no shell grammar — flows through the
existing `run` path unchanged (`runner.rs`, `run_with_env`) and returns
whatever `RunResult` already returns: the script's `exit_code`,
`stdout`, `stderr`. Nothing in the dispatch or the timeout handling
changes.

**C4 — Everything else stays refused.** The refusal path
(`main.rs:444-459@H`) is untouched; every name still absent from the
const — `curl`, `wget`, and the rest — is refused exactly as before.
The allowlist's size grows by one; its semantics grow by zero.

**C5 — `docker` is the next same-shaped need, recorded not done.**
Running a gate script inside a container (a migration repo's
`docker compose run …`) is the next admission this const will be asked
for. It is **named here and excluded from the row's done-when**: T1
adds `bash` only. Whether `docker` follows the same shape — name in
const, fixed argv, sub-command as first argument — is that ticket's
decision, with its own evidence, not a free rider on this one.

## 4. Scout facts

- F1 The const: `PERMITTED_COMMANDS` carries 16 names, no `bash` —
  `runner.rs:33-50@H`.
- F2 The match: basename-only, final path component — `runner.rs:56-64@H`.
- F3 The refusal: `!runner::is_permitted(command)` → `isError: true`,
  `stderr: "command not permitted: …"`, `exit_code: -1` —
  `main.rs:444-459@H`.
- F4 The pin: `non_permitted_command_is_blocked` asserts
  `!is_permitted("bash")` — `runner.rs:238@H`.
- F5 The return: `RunResult { stdout, stderr, exit_code, duration_ms }`
  — `runner.rs:66-71@H` — already carries the exit code C3 needs; no
  shape change.

## 5. Open for plan STOPs

- Whether the positive `is_permitted("bash")` assertion goes in
  `permitted_basename_is_allowed` or a new test — T1's placement, C2.
- Whether the script path argument needs any shape convention (absolute
  vs working-dir-relative) — today the args vector is passed through
  verbatim, and the brief does not add a rule; if T1 finds the exec
  server's working-dir contract already settles it, no new rule is
  written.
- Whether `bash` travels on every platform the exec server serves or is
  cfg-walled — the const has no platform gating today (F1), and the
  default is to follow the file's existing shape: one flat list.
