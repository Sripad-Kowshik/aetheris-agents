## 1. Scope

The capability: **`run_command` accepts `docker` as a permitted command
name**, so an agent can run a container step — fixed arguments of the
shape `compose run --rm …` — and receive the command's exit code.

The addition is **one name in one const**. The rule the const enforces
stays exactly as it is: a fixed argv vector, no interpreter grammar. No
pipes, no redirection, no shell strings — and, new with this name, no
recomposition of the sub-command: the args vector is passed through as
given, so `compose run --rm …` lives entirely in args, exactly as the
script path did for `bash` (BL-292).

## 3. Contract

**C1 — One addition to the const.**
`PERMITTED_COMMANDS` (`runner.rs:33-52@H`) gains `"docker"`. Nothing
else in the const moves — the BL-292 entry (`"bash"`, `:47-48@H`) and
its comment stay; `is_permitted/1`'s basename matching
(`runner.rs:58-64@H`) is untouched.

**C2 — The positive pin, not a flip.** The unit test that still
asserts a non-permitted name is refused
(`non_permitted_command_is_blocked`, `runner.rs:256-263@H`) is
**unchanged** — `docker` was never one of its assertions. The positive
arm gains the pin: `permitted_basename_is_allowed` asserts
`is_permitted("docker")` beside the BL-292 `bash` pin. The const
change and the pin land together; one without the other is a red
build or a silent widening, and both are wrong.

**C3 — A fixed-args call returns the command's exit code.** A
`run_command` call with `command: "docker"` and fixed args — `compose
run --rm …`, passed through as given — flows through the existing
`run` path unchanged (`runner.rs`, `run_with_env`) and returns
whatever `RunResult` already returns: the command's `exit_code`,
`stdout`, `stderr`. Nothing in the dispatch or the timeout handling
changes. The dispatch path itself is already name-agnostic and proven
by BL-292 T1's runtime pin (`run_bash_returns_the_existing_run_result`,
`runner.rs:204@H`); whether T1 adds a docker runtime pin or relies on
that precedent is the STOP item below.

**C4 — Everything else stays refused.** The refusal path
(`main.rs:444-459@H`) is untouched; every name still absent from the
const — `curl`, `wget`, and the rest — is refused exactly as before.
The allowlist's size grows by one; its semantics grow by zero.

**C5 — No next name is filed here.** BL-292 named `docker` as the next
same-shaped need and this row discharges that record. No further
same-shaped admission is filed by this brief: the const grows by
`docker` only, and the next ask — if one comes — gets its own row,
evidence, and brief.

## 5. Open for plan STOPs

- The runtime-pin shape for a daemon-dependent sub-command: `compose
  run` needs a daemon and a compose file, so a CI-stable pin is not
  automatic. Options T1 weighs: pin at `is_permitted` level plus the
  BL-292 dispatch precedent (no new runtime test), or a daemon-free
  runtime pin (e.g. `docker --version` or `docker compose version`)
  if the environments T1 targets have the binary. T1 decides and says
  so; the done-when's exit-code arm is about the path, not a live
  container.
- Whether the long-running shape (`compose run` builds images) needs
  any timeout note in the tool description — today the timeout/kill
  path exists (`run_with_env`) and the brief adds no rule; if T1 finds
  the description's wording already settles it, no new rule is
  written.
- Whether `docker` travels on every platform the exec server serves —
  the const has no platform gating (F1), and the default is the
  file's existing shape: one flat list.
