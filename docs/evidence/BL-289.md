# BL-289 — a native-Windows first run times out in admission before the loop starts

**Date filed:** 2026-10-06 · **Type:** missing capability — Windows
first-start inside the admission window · **Row:** BL-289 (open,
`docs/backlog-2026-06.md` §Harness) · **Design:**
`docs/aetheris/backlog/bl-289-windows-admission-timeout.md` ·
**Citations:** `H` = harness `aetheris` at `77cb0ab`; no agents-repo line

## The finding

On native Windows (the operator requires it — no WSL), a cold first run
can exceed the admission window before the loop ever starts:

1. **The outer admission call is bounded by GenServer's default 5 s.**
   `lib/aetheris/admission.ex:182@H` — `GenServer.call(__MODULE__,
   {:admit_and_supervise, config, origin, schedule})` with **no timeout
   argument**, so the effective bound is GenServer's default of 5 000 ms
   (the filing premise's "…, 5000" is the *effective default*, not a
   literal argument — recorded as read).

2. **The worker ready handshake has its own 5 s.**
   `lib/aetheris/worker/client.ex:9-10@H` documents it ("must respond
   with `{"status": "ready"}` within 5 seconds"), and
   `lib/aetheris/worker/client.ex:295@H` — `after 5_000 ->
   {:stop, :worker_init_timeout}` in the synchronous init handshake.

Windows makes both budgets tight on a cold start: process creation and,
specifically, antivirus scanning of the freshly built worker binary can
push the worker's readiness past 5 s, and the outer admission call —
which admits *and* supervises the start synchronously — times out with
the caller's `exit`, so the run never reaches the loop and the API call
errors instead of returning 202.

## What is and is not affected

Only the first start is in the finding's scope: once the worker binary
has been executed and scanned once, later starts are fast. But the
first start is the operator's first impression and is exactly what the
playground flow drives. The finding does not assert the two budgets are
the *only* Windows-tight waits (the 30 s tool-call timeout at
`client.ex:150-152@H` is generous by comparison) — it asserts the two
5 s walls above.

## Design brief posture

`docs/aetheris/backlog/bl-289-windows-admission-timeout.md` names the
two candidate fixes explicitly as **plan STOPs and picks neither**:

- **Skip-the-worker in admission:** the admission call need not wait for
  the worker handshake — 202 means "admitted", and a handshake failure
  can surface later in the run the way other post-admission failures
  do.
- **Raise the timeout(s):** make the outer admission timeout strictly
  longer than the worker handshake (one bounded value or a config key),
  so the two walls cannot race.

Choosing is the implementation ticket's decision; the row closes on the
behaviour, not the mechanism.

## Reproduction

Live-first (a native Windows host with no prior worker run) — not
producible in this checkout: the timing is the finding, and the code
cites above are the two walls. Static evidence: the two budget reads
above and the absence of any Windows-specific admission or handshake
budget (`git grep -n "windows\|msys\|mingw" lib/aetheris/admission.ex
lib/aetheris/worker/client.ex` → 0 hits at `H`).
