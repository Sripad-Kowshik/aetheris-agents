# BL-284 — the missing call: an HTTP client cannot start a run from an existing .exs and supply only the user turn

**Date filed:** 2026-10-06 · **Type:** missing capability — the finding is the
missing call, not the fix · **Row:** BL-284 (open,
`docs/backlog-2026-06.md`, §Harness) · **Design:** `docs/aetheris/backlog/bl-284-run-from-agent-file.md`
**Citations:** `H` = harness `aetheris` at `cf90264`; `A` = `aetheris-agents`
at `20ca539`.

---

## The finding

A caller that holds an agent file — the .exs `%RunConfig{}`/`%OrbConfig{}`
structs this repo ships — and wants to start it over HTTP with nothing but
the user turn has **no endpoint to call**:

1. **The only POST-that-starts-a-run is `POST /api/playground/runs`
   (`docs/aetheris/playground-api.md` §3.3@H), and it requires
   `system_prompt` inline** — required fields are `sandbox_id`, `provider`,
   `model`, `system_prompt` (§3.3, "Required fields"). It cannot name an
   agent file: the schema is closed, and the known client-settable field
   list has no `agent_path` key — any unrecognised key, including one that
   named a file, is a 422 `unknown_field` violation (§3.3, "Unknown
   fields"). A body supplying only a path and a user turn is refused twice
   over: `missing_required` (`system_prompt` absent) and `unknown_field`
   (`agent_path` not a known field).

2. **`load_agent_file/1` exists but is CLI-only** — defined at
   `lib/aetheris/cli/commands/run_helpers.ex:357@H`, under `cli/commands/`;
   `git grep -n "def load_agent_file" lib/` at `H` returns that one
   definition, none under `lib/aetheris/api/`. The API router
   (`lib/aetheris/api/router.ex@H`) exposes no route that loads an agent
   file.

So the reuse path for every agent this repo defines is: read the .exs with
human eyes, copy its `system_prompt` string into a JSON request by hand,
re-type its tool list, and hope the copy matches the file. That is not a
call an HTTP client can make; it is a transcription task with no
truth-maker. The alternative today is the CLI (`mix aetheris run <file>`)
plus the events streams — but the CLI is not an HTTP surface, and
BL-266's streams (§3.5/§3.6@H) made run *observation* an HTTP
capability while run *start-from-file* stayed CLI-only.

## Reproduction (static, from the tree at `H`)

```bash
git -C ../aetheris grep -n "def load_agent_file" lib/
# → lib/aetheris/cli/commands/run_helpers.ex:357:  def load_agent_file(path)
# (one hit — nothing under lib/aetheris/api/)

grep -n "Required fields" ../aetheris/docs/aetheris/playground-api.md
# → Required fields: sandbox_id, provider, model, system_prompt.

grep -n "unknown_field\|closed-schema\|Known .*client-settable" \
  ../aetheris/docs/aetheris/playground-api.md
# → the API is closed-schema; unrecognised keys — including typos —
#   produce a 422 rather than silently defaulting.
```

**The live curl is owed where the harness runs** (this checkout's harness
mirror has no `deps/`, so `Aetheris.API.Server` cannot be booted here):
`curl -X POST .../api/playground/runs` with body
`{"agent_path": "ct-bot/agents/main.exs", "user_prompt": "..."}` should
return 422 with a `policy_violation` envelope carrying both the
`missing_required` (`system_prompt`) and `unknown_field` (`agent_path`)
violations, per §3.3's normative contract. The static reading above is
the contract's own text; the curl confirms it and nothing more.

## What the capability is (and is not)

The missing call: *start a run whose configuration comes from a file on
disk, supplying only the user turn.* The fix's shape is T1 of the design
brief — a route whose body is `agent_path` + `user_prompt`, the path
confined to a configured agents root, `load_agent_file/1` doing the
loading, the request's `user_prompt` overlaying the file's, `202` with a
`run_id`, and the caller consuming the **existing** event streams
(§3.5/§3.6@H — no new transport). The done-when's named test reads the
`prompt_built` trajectory event (`lib/aetheris/execution/loop.ex:183@H`;
payload carries `system_prompt`, `user_prompt`, `tool_schema` per
`lib/aetheris/run_config.ex:59-62@H`): it must carry the **supplied**
`user_prompt` and the **file's** tool list — proving the overlay landed on
a file-derived config — and the request carried no `system_prompt`.
