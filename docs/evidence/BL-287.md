# BL-287 — no thread or owner field on runs: a host cannot keep a chat thread for an owner across machines

**Date filed:** 2026-10-06 · **Type:** missing capability — the finding is
the missing fields, not the fix · **Row:** BL-287 (open,
`docs/backlog-2026-06.md` §Harness) · **Design:**
`docs/aetheris/backlog/bl-287-owner-thread.md` · **Citations:** `H` =
harness `aetheris` at `327a30e`; `A` = `aetheris-agents` at `c733910`.

---

## The finding

A host that wants a chat thread per owner — the panel conversation
persisted under an owner id, listed and resumed after the browser moves
to another machine — has nothing to hang it on:

1. **No session, conversation, or owner field exists on the run surface.**
   `git grep -in "thread\|owner_id\|session" lib/aetheris/api/` at `H`
   returns zero hits. The API's run surface is `POST
   /api/playground/agent-file-runs` (BL-284, §3.7@H) — `agent_path` +
   `user_prompt`, exactly — and the read routes (`GET
   /api/playground/runs/:run_id` §3.4@H) key on `run_id` alone.

2. **Runs are flat.** The `runs` table
   (`lib/aetheris/store.ex:1033-1046@H`) is
   `run_id, status, config_json, started_at, finished_at, label,
   terminal_seq` — a run belongs to nothing. The run list a consumer sees
   is one flat list; there is no grouping key, no title, no ordering
   beyond time.

3. **SQLite is the only DB.** The store is Exqlite against one file
   (BL-266 F1: a single GenServer on one connection, `store.ex@H`). There
   is no second database to migrate a thread model into.

4. **The closed schema refuses a third key** — BL-284 C1.2, restated in
   `playground-api.md` §3.3@H's `unknown_field` rule: any request key
   beyond the known list is a 422. A host cannot smuggle `owner_id` or
   `thread_id` in today, and cannot set `label` to carry them (one string,
   no structure, and the schema has no field for it either — same
   `unknown_field` refusal on `agent-file-runs`).

## Multi-machine means one harness node, not a replicated store

The capability is: the **host** moves between machines; the harness does
not. The store stays exactly what BL-266's design made it — durable,
replicable-by-file, live-local (its C6: a non-terminal run streams only
from the hosting VM) — and this capability adds **fields on the run row
and two read routes**, not a second store, not a sync protocol, not a
session authority. The chat thread is the host's concept (a panel
conversation under an owner) that the run row learns to carry and list.
Nothing here proposes a replicated store, and the brief's store note
keeps the change inside the one SQLite file.

## Cite the survey

`docs/aetheris/harness-capabilities-appendix.md@H` — "the contract between
you and the harness" for a host designer working without repo access —
documents the execution model, the durable trajectory ("every step is
durably logged… the trajectory is the audit source of truth") and the run
lifecycle, and says nothing about sessions, conversations, owners, or
threads: a designer reading the survey would conclude a run cannot belong
to a chat thread. It cannot. That is the capability gap this row files —
the row does not edit the survey (C7-class: contract docs are amended by
the implementation ticket).

## No live curl required

The finding is absence in a schema and an API surface, provable from the
tracked tree at `H`: the greps above, the runs table DDL, and BL-284's
closed-field list. No server run is needed.
