# BL-294 — run_command refuses curl, so an api agent cannot run the gate curls

**Date filed:** 2026-10-28 · **Type:** missing capability — `curl` as a
permitted `run_command` name · **Row:** BL-294 (open,
`docs/backlog-2026-06.md` §Harness) · **Design:**
`docs/aetheris/backlog/bl-294.md` · **Citations:** `H` = harness
`aetheris` at `f76d92a`.

---

## The finding

The exec server's `run_command` still cannot execute an HTTP call,
because the command name is matched against the hardcoded allowlist
that BL-292 and BL-293 widened by one name each — `bash`, then
`docker` — and no more:

- `native/aetheris_exec_server/src/runner.rs:33-54@H` —
  `PERMITTED_COMMANDS`, now 18 names: the original 16 plus `"bash"`
  (BL-292 T1) and `"docker"` (`:50@H`, BL-293 T1, each with its own
  in-const comment). `"curl"` appears nowhere in the const.
- `runner.rs:60-66@H` — `is_permitted/1` matches only the command's
  final path component against that const (unchanged across both
  admissions).
- The doc comment above it (`:57-59@H`) even uses curl as its
  **refused example**: "`../../bin/curl` → `curl` → not permitted".

A name not in the const is refused at dispatch:
`native/aetheris_exec_server/src/main.rs:444-459@H` —
`handle_run_command` returns `isError: true` with
`stderr: "command not permitted: {command}"` and `exit_code: -1` for
any command whose basename is absent from the const.

The refusal is pinned by a unit test:
`runner.rs:274-281@H` — `non_permitted_command_is_blocked` asserts
`!is_permitted("curl")` at `:276@H` (and `wget` at `:277@H`; the
BL-292 T1 comment records bash's removal from the same test). Unlike
BL-293's docker — never pinned refused — **curl is an asserted
refusal in two test sites**: `path_traversal_attempt_is_blocked`
(`:283-287@H`) asserts `!is_permitted("../../bin/curl")` and
`!is_permitted("/usr/bin/curl")` (`:285-286@H`) because curl itself
was the refused name the traversal pin was written against. Admitting
curl therefore touches three sites — the refusal test's curl line,
the traversal test's two curl assertions, and the doc-comment example
— none of which can be silently dropped, because each pins something
real (the refusal mechanism; the basename-resolution semantics; the
documented example).

Consequence: an agent that must run the **gate curls** — a `GET` or
`POST` with fixed arguments, the shape the api gate names for its
read/write checks — has no permitted way to invoke them. The step
cannot be inlined as some other permitted binary: the point of the
curl is the HTTP call it makes. This completes a pattern the series
has been naming one step ahead of the code: bash (BL-292), docker
(BL-293), now curl — each a name an existing gate agent needs, each
refused by the same const.

## Reproduction

No live run required — the refusal is static and unit-pinned:

- `grep -n '"curl"' native/aetheris_exec_server/src/runner.rs` → the
  hits are all negative assertions and the doc-comment example;
  `"curl"` is absent from `PERMITTED_COMMANDS` (`:33-54@H`).
- `cargo test -p aetheris_exec_server non_permitted_command_is_blocked`
  at `H` passes with curl refused by the same mechanism the test has
  always pinned.
