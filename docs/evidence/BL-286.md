# BL-286 — a CORS preflight to the playground API is answered by the auth plug with 401

**Date filed:** 2026-10-06 · **Type:** missing capability · **Row:** BL-286
(open, `docs/backlog-2026-06.md` §Harness) · **Citations:** `H` = harness
`aetheris` at `324fe46`.

---

## The finding

An `OPTIONS` preflight from `http://localhost:4200` to
`POST /api/playground/agent-file-runs` is answered **401 by the auth
plug**, because the plug is pipeline-level, method-blind, and the
preflight carries no bearer token — browsers never send credentials on a
preflight. With no `Access-Control-Allow-*` headers in that 401, the
browser fails the preflight and refuses to send the actual `POST`. The
BL-284 route is therefore unusable from any browser origin **even with
valid credentials**. The route itself (BL-284) stays; this row is the
preflight.

The harness facts, all at `H`:

1. **The plug runs before matching, for every method.**
   `lib/aetheris/api/playground_router.ex:27@H` — `plug(AuthPlug)` at
   module level; the module's own doc (`:6-9@H`) states it is "placed
   before" matching and that unauthenticated requests to *any* playground
   route are rejected there (`:9@H`).
2. **The plug is method-blind.** `lib/aetheris/api/auth_plug.ex:47-53@H` —
   `call/2` has two arms (`{:ok, presented}` → token check; `:missing` →
   `reject/1` → 401). No `OPTIONS` branch exists; a preflight is just
   another request with no credential.
3. **No CORS handling exists anywhere in the API.**
   `git grep -rn "OPTIONS\|CORS\|cors\|Access-Control" lib/aetheris/api/`
   → zero hits at `H`.
4. **The normative contract is silent on preflight too.**
   `docs/aetheris/playground-api.md` has zero `OPTIONS`/CORS/
   `Access-Control` hits at `H` — the §4 envelope and §5 auth scheme
   document neither the exemption nor any origin allowlist.

## The scenario and its origin

`http://localhost:4200` is the Angular dev server's default origin — the
panel host the ct-bot milestone names as its transport ("Panel transport
(Angular host, port 4001)", `ct-bot/milestone.md` §Exit criterion). The
host arrives in a later milestone, but the gap is in the API now: the
first browser page that tries to call BL-284's route hits this 401
preflight on day one.

## Reproduction

Static, from the tree at `H` — the greps above (plug placement, no
OPTIONS arm, zero CORS hits in code and contract). The live curl is owed
where the harness runs (no `deps/` in this checkout's mirror):

```bash
curl -i -X OPTIONS \
  -H "Origin: http://localhost:4200" \
  -H "Access-Control-Request-Method: POST" \
  http://localhost:4001/api/playground/agent-file-runs
# observed expectation at H: 401 + the §4@H envelope, no Access-Control-* header
# after the fix (the done-when): 204 before auth, with the allow headers

curl -i -X POST http://localhost:4001/api/playground/agent-file-runs
# at H and after the fix: 401 — the second arm of the done-when
```

## What the done-when asks, and the one constraint recorded here

- "OPTIONS from that origin returns **204 before auth**": the preflight
  short-circuits before token validation. "That origin" — the allowlist
  decision (which origins, which config key, localhost defaults) is the
  fix round's, guided by §6@H's localhost-default posture.
- "a POST with no bearer still returns **401**": the fix must not weaken
  the token model — the preflight is unauthenticated because the browser
  rules make it so, not because the route became public.
- Recorded fact the fix must respect, not a design: the
  `PlaygroundRouter` doc says "Do not reorder the plugs" (`:12@H`) — the
  short-circuit has to coexist with that constraint.
