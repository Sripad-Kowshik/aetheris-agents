# BL-288 — the preflight allow-methods list refuses GET, so a browser cannot call any playground read route

**Date filed:** 2026-10-06 · **Type:** missing capability — the finding is
the missing method, not the fix · **Row:** BL-288 (open,
`docs/backlog-2026-06.md` §Harness) · **Design:**
`docs/aetheris/backlog/bl-288-get-preflight.md` · **Citations:** `H` =
harness `aetheris` at `91d6a85`; `A` = `aetheris-agents` at `c733910`.

---

## The finding

BL-286's preflight short-circuit answers an allowed-origin `OPTIONS`
with `204` before auth — but only for the methods it knows:

- `lib/aetheris/api/cors_plug.ex:47@H` — `@allowed_methods ["POST",
  "DELETE"]`; the allow-methods header is emitted from that list
  (`:95@H`).
- `docs/aetheris/playground-api.md` CORS preflight block (:863-889@H) —
  "**Allow methods:** `POST, DELETE` — the playground namespace's
  mutating methods."

**GET is absent from the list.** A browser `GET` that carries
`Authorization` is a **non-simple request** — `Authorization` is not a
CORS-safelisted request header — so the browser preflights it, sending
`Access-Control-Request-Method: GET`. The plug's method set does not
include GET, so the preflight is refused and the browser blocks the real
GET. Every playground read route is unreachable from a browser page:

- `GET /api/playground/runs/:run_id` (§3.4@H) — today's run-status GET.
- The two event streams (§3.5/§3.6@H) — both GET, and the SSE section
  already notes browser clients must read them with `fetch` because they
  carry `Authorization` (§3.5@H) — which is exactly the non-simple
  request this preflight refuses.
- BL-287's planned read routes (`GET` the owner's threads and a thread's
  runs, its C6) — the routes this row's ticket cites as the motivation:
  filed next to BL-287, blocked by BL-288.

## Cite BL-286 and BL-287

- **BL-286** (closed 2026-10-06): the preflight short-circuit exists and
  weakened nothing — its own done-when's second arm (a bearerless POST
  still 401) held. The **method list** is the remaining hole; this row
  does not revisit the origin allowlist, the header list, or the auth
  ordering.
- **BL-287** (open): its two new GET routes are the capability this row
  unblocks. Filed after it so the dependency is visible: BL-287's list
  routes are dead on arrival from a browser origin until the allow-list
  includes GET.

## No live curl required

Static absence is enough: the method list is a two-element literal in a
tracked file (`cors_plug.ex:47@H`) and the contract text names the same
two methods (`playground-api.md@H`). The greps above are the proof; a
live preflight would show the same refusal with the same two methods in
the response header.

## The non-simple premise, stated once

"Non-simple" is the CORS fetch spec's own test: a request whose method
is outside GET/HEAD/POST, whose content-type is not the safelisted
trio, or which carries a non-safelisted header (Authorization included)
requires a preflight. This row's whole finding rests on that sentence —
a GET *without* Authorization would be simple and preflight-free, but
every playground read route is bearer-gated, so every browser GET to
them is preflighted and every preflight asks for GET.
